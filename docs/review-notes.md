### P0-5. 라이브러리 4개가 아직 없는 SDK를 요구했습니다 · 담당: 🧠 설계 (해결됨)

빌드해 보고서야 드러난 문제입니다. 첫 빌드가 `checkDebugAarMetadata` 단계에서
**31건**으로 멈췄습니다.

```
Dependency 'androidx.compose.ui:ui-android:1.12.0' requires ...
    compile against version 37 or later of the Android APIs.
    :app is currently compiled against android-36.
Dependency ... requires Android Gradle plugin 9.1.0 or higher.
```

**원인:** 1단계에서 의존성 20여 개가 Maven 에 **존재하는지**는 전부 확인했지만,
서로 **호환되는지**는 확인하지 않았습니다. 각 AAR 안에는
`META-INF/com/android/build/gradle/aar-metadata.properties` 가 들어 있고
거기 `minCompileSdk` 가 적혀 있습니다 — AGP 가 검사하는 바로 그 값입니다.
빌드를 반복하지 않고도 AAR 을 열어 읽으면 알 수 있는 값이었습니다.

**막다른 길:** AGP 를 9.3.1 로 올리고 compileSdk 를 37 로 올려 봤지만,
`platforms/android-37` 이 **아직 정식 채널에 없습니다**
(`Package platforms/android-37 not found`). 라이브러리가 미출시 플랫폼을
앞서 요구하는 상태입니다.

**해결:** 정식 최신 플랫폼인 36 에 맞는 버전으로 내렸습니다.

| 라이브러리 | 이전 | 요구 | 지금 | 요구 |
|---|---|---|---|---|
| Compose BOM | 2026.08.00 (ui 1.12.0) | **37** | 2026.06.01 (ui 1.11.4) | 35 |
| core-ktx | 1.19.0 | **37** | 1.18.0 | 36 |
| lifecycle | 2.11.0 | **37** | 2.10.0 | 35 |
| okhttp | 5.5.0 | **37** | 5.4.0 | 36 |

남은 최대 요구가 AGP 8.9.1 이라 AGP 8.13.2 · Gradle 8.14.3 은 그대로 두었습니다.
이유는 `gradle/libs.versions.toml` 주석에 적어 두었습니다.

**앞으로:** `platforms/android-37` 이 정식 공개되면 위 네 개와 AGP 9.x 를 함께 올리면 됩니다.
버전을 올릴 때는 **Maven 에 있는지가 아니라 AAR 의 `minCompileSdk` 를** 확인하세요.

## 4. Ride / Wait 로직 점검

### 기획서 로직: 대기 비용 vs 혼잡도 감소

`domain/usecase/RideOrWaitDecider.kt`를 읽고 규칙을 그대로 옮기면 이렇습니다.

| 규칙 | 조건 | 결론 |
|---|---|---|
| 8 | 막차 | RIDE |
| 2 | 다음 열차 정보 없음 | RIDE |
| 7 | 신뢰도 LOW | RIDE |
| 3 | 등급 같음 | RIDE |
| 6 | 다음이 더 나쁨 | RIDE |
| **4** | **두 등급 이상 개선** | **WAIT — 대기 시간을 보지 않음** |
| 5 | 한 등급 개선 + 대기 ≤ 4분 | WAIT |
| 5' | 한 등급 개선 + 대기 > 4분 | RIDE |

### 🔴 발견: 규칙 4에 대기 시간 상한이 없습니다 · 담당: ⚙️ 데이터·기능

```kotlin
// RideOrWaitDecider.kt:100
if (levelGain >= 2) {
    return wait(...)   // waitSeconds 를 조건에 쓰지 않습니다
}
```

**증상:** 다음 열차가 두 등급 낫기만 하면 **20분을 기다리라고 해도 WAIT**입니다.
막차 직전 배차가 벌어졌을 때 실제로 나올 수 있는 상황입니다.

**왜 문제인가:** 기획의 핵심이 "대기 비용 vs 혼잡도 감소"인데, 이 분기만 **대기 비용을 0으로 취급**합니다.
규칙 5는 4분 상한을 두면서 규칙 4는 무한대를 허용하는 것은 일관성도 없습니다.

**제안:** 등급 개선폭에 따라 상한을 두는 편이 기획에 맞습니다. 예를 들어
한 등급 = 4분, 두 등급 = 8분, 세 등급 이상 = 12분처럼요. 상한을 넘으면 RIDE 로 가되
"다음 열차가 훨씬 낫지만 N분을 기다려야 합니다"라고 알려 주면 사용자가 직접 판단할 수 있습니다.

- [x] **수정 완료** — 제안 그대로 넣었습니다. 자세한 내용은 12-3.

### 나머지 규칙은 타당합니다

특히 **규칙 7(신뢰도 LOW → RIDE)** 은 좋은 판단입니다. 근거가 약한데 사용자를 플랫폼에
세워 두는 것이 가장 나쁜 조언이라는 설계 의도가 코드와 주석에 일관되게 반영돼 있습니다.

단위 테스트(`app/src/test/.../RideOrWaitDeciderTest.kt`)가 규칙 8개를 모두 덮고 있습니다. 좋습니다.

## 10. 칭찬할 만한 것

문제만 적으면 균형이 안 맞으니 잘된 것도 남깁니다.

- **API 검증이 문서가 아니라 실측입니다.** 샘플 키의 5건 제한, `barvlDt`가 0으로 오는 함정,
  에러일 때 XML이 오는 문제 — 전부 실제로 호출해 보고 찾아낸 것들이라 신뢰가 갑니다.
- **정직함이 코드에 박혀 있습니다.** 어림값은 `APPROXIMATED`로 표시되고, 그 값은 절대
  신뢰도 `HIGH`가 되지 않으며, 신뢰도가 낮으면 숫자를 숨기고 농담도 하지 않습니다.
  "모르면 모른다고 한다"가 도메인부터 화면까지 일관됩니다.
- **색이 눈대중이 아닙니다.** 다크 모드 대비를 수치로 재고(전부 3.6:1 이상, 인접 등급 ΔE 37 이상),
  라이트 모드가 대비 미달인 것을 발견해 고쳤습니다.
- **문구 분리가 깔끔합니다.** 장난 36개 / 담백 10개가 한 문장도 겹치지 않고,
  판단이 `HellCopy.toneFor()` 한 곳에 모여 있습니다.
- **광과민성 발작을 고려했습니다.** 혼잡 구간을 깜빡이는 대신 1.9초 주기로 숨쉬게 했고,
  시스템의 "애니메이션 끄기" 설정을 존중합니다.

### 켜 보니 맞았던 것

- **시간대 처리가 정확합니다.** 에뮬레이터 시계는 08:53(UTC)인데 앱은 **17:30 "지금"** 을

- 다크 모드 팔레트가 라이트 모드만큼 읽힙니다. 노선 색·환승 표시·마스코트 전부 정상.

### 11-1. 🔴 지도가 화면의 41%만 썼습니다 · 담당: 🎨 화면 → ✅ 완료

원인이 두 겹이었습니다.

```kotlin
// MetroMapView.kt (전)
fun contentSize(size: Size) = min(size.width, size.height) * FIT_RATIO
```

짧은 변에 맞추니 세로로 긴 폰에서 **정사각형에만** 그렸습니다. 게다가 도식 좌표가 정규화
공간을 다 쓰지 않아(가로 76% · 세로 60%) 그 정사각형 안에서 또 줄었습니다.

**수정:** `MetroLayout`에 `MetroBounds`를 두어 배치가 **자기 내용의 실제 경계**를 들고 있게 하고,
그리는 쪽이 그 경계를 화면에 맞추도록 바꿨습니다. 중앙 기준점도 `0.5`가 아니라 내용의
한가운데를 쓰고, 이동 제한도 실제로 그려지는 가로·세로 길이를 각각 씁니다.

```
1080 × 1100 자리에서   전 756 × 636 (41%)  →  후 1032 × 804 (70%)
```

세로가 남는 것은 정상입니다. 노선도가 1.26:1이라 세로까지 채우려면 지도를 찌그러뜨려야 합니다.

### 11-2. 🔴 같은 문장이 한 화면에 세 번 · 담당: 🎨 화면 → ✅ 완료

역 상세에서 "이 방향 열차 정보가 없습니다"가 안내 배너·마스코트 대사·하단 카드에 세 번 났습니다.

원인은 `HellCopy.plainHeadline()`이 **운행 상태를 혼잡도보다 먼저 봤기** 때문입니다.
열차 정보가 없으면 제목이 통째로 운행 상태 문장으로 바뀌면서, 바로 위 배너와 같은 말을
반복하고 정작 알고 있던 혼잡도는 버렸습니다.

**수정:** 순서를 뒤집어 **등급을 아는 동안에는 등급을 말하도록** 했습니다. 열차가 안 와도
역이 붐빈다는 사실은 그대로입니다. 도착 목록이 빌 때 쓸 문구는 `HellCopy.emptyTrains()`로
따로 뒀습니다 — 제목·배너와 겹치지 않게 **열차 이야기만** 합니다.

### 11-3. 🔴 배지와 본문이 서로 반대말 · 담당: 🎨 화면 → ✅ 완료

배지는 "혼잡", 게이지는 절반 주황인데 본문은 "정보 없음"이었습니다. 실제로는 *역* 어림값은
있고 *열차* 정보만 없는 상태인데 화면이 둘을 구분하지 않았습니다.

11-2로 역 상세는 해결됐고, 남은 결과 화면은 `CrowdGauge`에 `label`을 받게 해서
**"역 기준 혼잡도"**를 붙였습니다. NOW/NEXT 카드가 "정보 없음"이어도 아래 막대가 무엇을
재는지 읽힙니다.

### 11-4. 🟡 자주 찾는 역이 1호선으로 쏠림 · 담당: ⚙️ 데이터 → ✅ 완료

```
후  종로3가 고속터미널 신당 을지로4가 을지로3가 왕십리 건대입구 잠실 종합운동장 시청
```

### 11-5. 🔴 "지옥할 것으로 보입니다" · 담당: 🎨 화면 → ✅ 완료

### 12-1. 로딩과 실패 구분 (5-1) · ✅

**고치다 보니 원인이 다른 데 있었습니다.** 화면이 실패를 안 그린 게 아니라,
실패가 화면까지 오지 않고 있었습니다.

```kotlin
// GetStationBoardUseCase (전) — 실패든 로딩이든 똑같이 빈 목록으로 뭉갭니다
when (loaded) {
    is Loadable.Ready -> { ... }
    else -> { allArrivals = emptyList(); isArrivalFallback = true }
}
```

실시간을 못 받아도 통계로 화면을 채우는 것 자체는 옳습니다. 문제는 **왜** 못 받았는지가
그 자리에서 사라진다는 것이었습니다. 그래서 사용자에게는 "지금 오는 열차가 없다"와
"신호가 끊겼다"가 **같은 문장**으로 보였습니다. 앞은 기다리면 되고 뒤는 다시 눌러야
하는데도요.

**수정:** `StationBoard`에 `arrivalFailure: UnavailableReason?`를 실어 화면까지 나릅니다.
화면에는 `ui/component/LoadFailure.kt`가 이유별 문구와 함께 뜹니다.

**"다시 시도"를 늘 주지는 않습니다.** 인증키가 없거나 운행 시간이 아닌 것은 다시 눌러도
그대로입니다(`HellCopy.isRetryable`). 눌러도 안 되는 버튼은 없느니만 못합니다.

에뮬레이터에서 비행기 모드로 확인한 실제 흐름입니다.

```
비행기 모드 ON  →  "지금은 연결이 안 됩니다"       + [다시 시도]
비행기 모드 OFF →  다시 시도를 누르면 이유가 바뀝니다
                →  "이 역은 실시간 조회 범위 밖입니다"  (버튼 없음 — 인증키 문제라 눌러도 소용없음)
```

두 번째 문장이 이번 수정의 값어치입니다. 예전 같으면 둘 다 "이 방향 열차 정보가 없습니다"
한 줄이었고, 사용자는 인증키가 없다는 사실을 영영 알 수 없었습니다.

### 12-2. 자동 갱신 (5-3) · ✅

`now: Instant = Instant.now()`가 **기본값**이라 처음 그려질 때 한 번만 정해졌습니다.

**수정:** `ui/state/HellClock.kt`에 박자를 둘 만들었습니다.

| | 간격 | 무엇에 쓰나 |
|---|---|---|
| `rememberNow()` | 1초 | 남은 시간이 실제로 줄어들도록 |
| `rememberDataRefreshKey()` | 30초 | 도착 정보를 다시 부르도록 |

시각 자체를 조회 열쇠로 쓰면 **초당 한 번씩 지하철 API를 두드리게 됩니다.** 그래서 나눴습니다.
30초는 서울 지하철 최저 배차(2분 남짓) 기준으로 한 열차를 놓치지 않는 간격입니다.

둘 다 `RESUMED` 동안에만 돕니다 — 주머니 속에서 30초마다 API를 부르면 사용자에게
아무 값어치도 없이 배터리와 데이터만 씁니다.

다시 부를 때 **이전 값을 지우지 않습니다.** 30초마다 화면이 빈칸으로 깜빡이면
고장 난 것처럼 보입니다.

> **아직 눈으로 못 본 것:** 인증키가 없어 열차 도착 시각 자체가 안 나오므로,
> **"3분 후"가 실제로 줄어드는 장면은 확인하지 못했습니다.** 75초 동안(갱신 2회) 화면이
> 비거나 깜빡이지 않는 것은 확인했습니다. 인증키가 생기면 이건 다시 봐야 합니다.

### 12-3. Ride/Wait 규칙 4 대기 상한 (4장) · ✅

검토에서 제안한 그대로 넣었습니다 — 한 등급 4분, 두 등급 8분, 세 등급 이상 12분.

```kotlin
private fun waitLimitFor(levelGain: Int): Int =
    SHORT_WAIT_SECONDS * levelGain.coerceIn(1, MAX_WAIT_STEPS)
```

상한을 넘으면 RIDE로 가되 **얼마나 나은지는 그대로 알려 줍니다** — "다음 열차는 여유로
훨씬 낫지만 10분을 기다려야 합니다. 지금 타세요." 사용자가 직접 판단할 수 있어야 합니다.

대기 시간을 모를 때(`waitSeconds == null`)도 RIDE로 갑니다. 규칙 5가 이미 그렇게 하고
있었고, "근거가 약하면 RIDE로 기운다"는 이 파일 전체의 원칙과도 맞습니다.

세 등급 넘게 벌어져도 12분에서 멈춥니다. 그보다 오래 기다리면 **얼마나 나아지든**
지하철을 타러 온 목적 자체가 흐려집니다.

단위 테스트 2개를 더 넣었습니다(11 → 13개). 경계값 8분/8분 1초, 12분/12분 1초를 짚습니다.

### 12-4. Settings 화면 + 출처 표기 (3장 8번 · 6장) · ✅

**라이선스 의무가 먼저입니다.** 서울교통공사 혼잡도 통계는 공공누리 제3유형이라
출처 표시가 의무인데, 표시할 화면 자체가 없었습니다. 설정 화면이 없다는 것은 곧
의무를 어기고 있다는 뜻이었습니다.

넣은 것:

| 칸 | 내용 |
|---|---|
| 화면 | 기기 설정 / 밝게 / 어둡게 |
| 기본 방향 | 상행 / 하행 — 출퇴근은 매일 같은 방향이라 한 번 덜 누릅니다 |
| 지금 보는 값 | 역 수 · 실시간 · 실측 통계 갖춤 여부, 그리고 **% 숫자가 왜 안 나오는지** |
| 데이터 출처 | 서울교통공사(공공누리 제3유형) · 서울 열린데이터광장 |
| 혼잡도 기준 | 100%는 "꽉 참"이 아니라 정원이라는 설명 |

"지금 보는 값" 칸을 넣은 이유: % 숫자를 숨기는 것은 **일부러 만든 규칙**인데, 사용자
눈에는 그냥 기능이 빠진 것처럼 보입니다. 어딘가에서는 설명해야 합니다.

저장은 `data/local/settings/AppSettingsStore.kt`(DataStore). 역 목록 캐시와 **다른 파일**을
씁니다 — 캐시는 형식이 바뀌면 통째로 버리지만 사용자가 정한 값은 같이 날아가면 안 됩니다.
값은 enum 순번이 아니라 이름으로 저장합니다. 순번으로 저장하면 나중에 항목 순서를 바꿀 때
저장된 값의 뜻이 조용히 달라집니다.

앱을 완전히 종료했다가 다시 켜서 어두운 테마와 하행이 유지되는 것을 확인했습니다.

**즐겨찾는 역은 넣지 않았습니다.** 저장뿐 아니라 지도·검색까지 손대야 하는 별개의 기능이라,
설정 화면 하나로 끝나지 않습니다. 3장에 남겨 두었습니다.

### 13-1. Time Slider 어긋남 + Time Travel 확장 (7-2 · 3장) · ✅

슬라이더를 08:30으로 옮기고 역을 누르면 **08:30 예상 혼잡도**와 **지금 들어오는 열차**가
한 화면에 섞여 있었습니다.

**수정:** 역 시트가 `viewingSlot`을 받습니다. 지금이 아닌 시간대를 보는 중이면 열차 목록과
결론("타세요/기다리세요")을 **통째로 감추고** 그 자리에 이렇게 씁니다.

```
08:30 기준 예상 혼잡도입니다
열차 도착 정보는 지금 시각에만 보여드립니다
```

자리를 그냥 비우지 않은 이유: 비어 있으면 사용자는 "왜 열차가 안 나오지" 하고 앱을
의심합니다. 없는 이유를 말해 주면 납득합니다.

**경로 결과 화면에는 Time Travel을 넣지 않았습니다.** Ride/Wait 판단은 *지금 들어오는
실제 열차 두 대*를 비교하는 것이라, 시간을 옮기면 비교할 대상 자체가 없습니다.
"3시간 뒤에 탈까 기다릴까"는 대답할 수 없는 질문입니다. 혼잡도(지도·역 상세)에만
시간여행이 뜻이 있습니다.

### 13-2. 구간 혼잡도 표시 (7-3) · ✅

역 점만 칠하면 "이 역이 붐빈다"는 알아도 **"이 구간을 타고 가면 어떤가"** 는 모릅니다.
지하철은 역에 서 있는 게 아니라 구간을 타고 가는 것입니다.

**수정:** 노선 선을 구간마다 나눠 그리고, 혼잡도를 **굵은 후광**으로 얹었습니다.
노선 색은 그 안의 **심**으로 남깁니다 — 사용자가 외우고 있는 노선 색을 덮으면 지도를
못 읽습니다. 처음엔 후광을 1.9배로 넣었다가 노선 색이 안 보여서 1.45배로 줄였습니다.

구간 혼잡도는 그 구간이 **출발하는 역**의 값을 씁니다. `HellStationFacade.segmentCrowd()`와
같은 규칙이라 지도 색과 숫자가 어긋나지 않습니다.

성능 때문에 구간마다 `drawLine`을 부르지는 않습니다. 지도에 구간이 300개가 넘고 맥박
애니메이션 때문에 매 프레임 다시 그려지므로, **등급이 같은 구간끼리 하나의 경로로 묶어**
등급 수(최대 5)만큼만 그립니다.

### 13-3. 지도 접근성 + 죽은 BROWSE 분기 (7-4 · 7-5) · ✅

**두 문제가 같은 답을 갖고 있었습니다.**

- 7-4: 지도는 Canvas에 그린 그림이라 스크린리더가 역 306개를 읽지 못합니다.
- 7-5: `SearchPurpose.BROWSE`가 정의만 돼 있고 아무도 안 씁니다.

BROWSE 검색이 곧 **"목록으로 역 고르기"** 입니다. 그래서 지우는 대신 진입점을 만들었습니다.
지도 오른쪽 확대 단추 밑에 `⌕` 하나를 더 놓았습니다(`역을 목록에서 찾기`).
위쪽 막대는 이미 경로 검색 + 설정으로 꽉 차 있어서, 좁은 화면에서 제목이 잘릴 위험이
있었습니다.

지도 전체 `contentDescription`도 고쳤습니다 — 이제 **어디로 가면 역을 고를 수 있는지**를
말해 줍니다.

```
Heatmap ─ [역 찾기] ─▶ Search(BROWSE) ─▶ StationDetail
```

### 13-4. 역 상세를 전체 화면으로 (7-6) · ✅

역을 직접 열면 `ResultScreen`이 떠서, 어디로 갈지 말한 적도 없는데 **"모르겠어요"가
화면 가득** 나왔습니다.

**수정:** `ui/station/StationDetailScreen.kt`를 새로 만들어 지도 시트와 **같은 내용**을
전체 화면으로 보여줍니다. 결과 화면은 출발역과 도착역이 다 정해졌을 때만 나옵니다.

### 13-5. 즐겨찾는 역 (3장) · ✅

12장에서는 "설정 화면 하나로 끝나지 않는다"며 미뤘는데, P2를 마저 하면서 넣었습니다.

- 역 시트·역 상세 제목 옆에 별(`☆`/`★`). 아이콘을 두 개 들여오지 않아도 됩니다
- 검색 화면에서 즐겨찾는 역이 맨 위로

**처음엔 순서만 바꿨다가 안 되는 걸 발견했습니다.** 환승이 없는 작은 역은 애초에
"자주 찾는 역" 목록에 들어오지 않으므로, 즐겨찾기를 해도 화면에 나타나지 않았습니다.
안국역(환승 없음)으로 확인했습니다. 그래서 **순서를 바꾸는 게 아니라 목록에 넣도록**
고쳤습니다. 출퇴근에 쓰는 역이 꼭 큰 역인 것도 아닙니다.

저장은 `StationId.key` 문자열입니다. `StationId`로 되돌리려면 노선 코드를 다시 해석해야
하는데, 모르는 코드가 섞이면 통째로 실패할 수 있습니다. 화면에서 비교만 하면 되는
값이라 문자열이 안전합니다.

### 남은 것

**6장① 배포 시 인증키 노출**은 고칠 문제가 아니라 **사람이 판단할 일**입니다.

쿼터를 남이 쓸 수 있습니다. **배포를 실제로 할 때** 판단해 주세요.

## 14. 노선도 손보기와 그때 나온 버그 (2026-08-25)

사용자가 실제 지하철 앱 노선도를 보여주며 "지금 너무 보기 불편하지 않냐"고 했습니다.
그 노선도 이미지는 저작물이라 쓸 수 없고, **그림 한 장이라 역마다 색을 칠할 수도 없습니다.**
대신 그 노선도가 읽기 쉬운 이유를 가져왔습니다.

| 고친 것 | 왜 |
|---|---|
| 45°·90°로만 꺾이게 | 실제 노선도가 전부 이렇게 그려집니다. 임의 각도로 이으면 도심에서 어느 선이 어디로 가는지 분간이 안 됩니다 |
| 이름을 기본 배율부터 | 예전엔 1.8배로 확대해야 나왔습니다. 이름 없는 노선도는 색깔 있는 점 무더기라 확대할 마음조차 안 듭니다 |
| 겹치는 이름은 숨김 | 환승이 많은 역이 먼저 자리를 잡고, 밀린 이름은 확대하면 나타납니다 |
| 잘릴 이름은 안 그림 | 확대 단추 밑에 깔려 "종합운.."처럼 반쪽만 보이던 것 |
| 같은 이름 중복 제거 | 신길처럼 여러 노선에 걸친 역이 이름을 두 번 찍었습니다 |

### 14-1. 🔴 Time Slider가 지도에 전혀 반영되지 않았습니다 · ✅

**README용 스크린샷을 찍다가 발견했습니다.** 08:00으로 옮겼는데 지도가 전부 회색이었습니다.

```kotlin
// HellStationData.kt (전)
snapshot = facade.heatmapAt(at),   // at = 지금. slot 은 쓰이지도 않습니다
```

슬라이더가 가리키는 **시간대를 실제 시각으로 바꾸는 줄이 빠져** 있었습니다.
지도는 슬라이더와 무관하게 늘 "지금"을 보여주고 있었습니다.

**왜 여태 못 봤나:** 시각이 지나면서 색이 저절로 바뀌니, 슬라이더를 움직였을 때 색이 달라
보이면 슬라이더가 듣는 줄 알았습니다. 12장에서 시간여행을 손볼 때도 **역 시트만** 확인했고
(시트는 `instantFor`를 제대로 쓰고 있었습니다) 지도는 확인하지 않았습니다.

`facade.instantFor(slot, at)`을 거치도록 고쳤습니다. 08:00에서 지도가 지옥으로 물듭니다.

**교훈:** "화면이 바뀌었다"와 "내가 바꾼 값 때문에 바뀌었다"는 다릅니다.
시간에 따라 저절로 변하는 화면은 **시간을 고정해 놓고** 확인해야 합니다.
